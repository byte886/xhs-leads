## 一、一句话结论

登录链路的病根不在任何一个 bug，而在**同一个"是否已登录"有三个互不相同的判据，且"打开登录页"有四条互不相让的路径**。这一轮把判据收成一份、把会误杀窗口的动作全部拆掉；架构上"登录页放在壳窗里"是否成立，仍需拍板。

## 二、登录态是怎么判出来的（修前 → 修后）

| 判据 | 位置 | 修前逻辑 | 问题 | 修后 |
|---|---|---|---|---|
| ① `_engine_login_state` | `server.py:286` | `id_token` 存在 → **直接判已登录**，完全不看页面 | 假阳性主要来源：cookie 残留但页面整页游客态 | 页面**明确**游客态 → 一律否决；页面读不到才用 `id_token` 兜底 |
| ② `xhsIsLoggedIn()` | `extension/lib/extract.js:277` | 要存在 `.avatar`/`.user-menu`，且无 login DOM/文本 | 本身没错，但被 ① 短路，实际没生效 | 保留，作为 ① 里的辅助分支 |
| ③ `_page_needs_login` | `browser_client.py:568` | 手机号 placeholder / 「登录探索更多内容」 | 与 ① 口径不一致：采集侧说游客态、后端说已登录 | 提升为公共常量 `NEEDS_LOGIN_JS`，**① 复用同一份 JS** |
| ④ `has_login_cookie` | `shell_window.py:748` | 只看 cookie 名是否存在 | 最弱，曾用来决定"要不要关登录页"→ 关掉用户正在扫码的页面 | 已不再用于关闭判定 |

**修后唯一口径**（按优先级）：

```
被踢信号（登录超限/请重新登录/登录已过期）  → 未登录
页面明确游客态（手机号框/登录探索更多内容） → 未登录（否决一切 cookie 结论）
id_token 存在                              → 已登录（仅当页面读不到时生效）
web_session + 页面头像判定                  → 已登录
其余                                        → 未登录
```

对应单测：`tests/test_login_chain.py::test_guest_render_vetoes_id_token` 等 4 条。

## 三、谁在打开登录页（四条路径 → 现状）

| 入口 | 触发者 | 修前动作 | 修后 |
|---|---|---|---|
| `POST /api/auth/login_begin` → 守卫 | APP「去登录」（`ForceLogin.vue`，force=true）、设置页「重新登录」（force=false） | 守卫把**壳窗**（Tab1，APP 主界面）`load_url` 成 `/login` | 不变（符合历史拍板「壳内直接加载登录页」），但新增窗口保护 |
| `GET /api/qrcode` | 历史入口 | `mirror.open_login` → 无小红书页时 `new_page` + `/login` | 已有小红书页则复用，不重复开窗 |
| `POST /api/mirror/open` | 登录小窗截图流 | 同上 | 同上 |
| `_refresh_engine_after_inject` | Cookie 注入后 | **关闭旧的小红书页 → 新开 `/login`** | **不关闭任何页面**；已有 `/login` 直接复用 |

**这一轮的自杀事故就发生在第四行**：点「去登录」时壳窗已被守卫导航到 `/login`，刷新逻辑把它当成"旧的小红书页"关掉 → keeper 把这次 close 判成"用户关了主窗口"→ 应用退出。

## 四、鼠标点「去登录」到底发生了什么（完整时序）

```
① 前端 ForceLogin.vue → apiLoginBegin(force=true)
② 后端 /api/auth/login_begin：置 gate.pending / force → 唤醒守卫线程
   同时 collapse_debug_windows() 收起 Tab2（登录引导期间右窗不留）
③ 守卫 login_guard 醒来 → 打日志「切换到小红书登录页」
   → _guard_navigate_to_login：
     · force=true 时先 clear_domain_cookies("xiaohongshu.com")（让登录页呈现扫码界面）
     · win.load_url(/login)  ← 壳窗文档被换掉，APP 主界面此刻已不可见
     · 再补一次 evaluate_js(window.location.href=/login)（双保险）
     · 注入 force_login（弹窗锁）/ login_fit（居中适配）/ login_clean（净化）
④ 守卫每 ~1s 读 context.cookies()：出现 web_session/id_token → POST /api/auth/import_cookies
⑤ import_cookies：写 cookie 进引擎 → _refresh_engine_after_inject（刷新使新文档带上登录态）
⑥ 验证通过 → gate 清 → 守卫把壳窗 load_url 回 APP（base/）
```

**风险点集中在 ③ 与 ⑤**：③ 期间壳窗的身份是"一个加载着小红书的窗口"，⑤ 若对它动手（close/reload）就触发自我退出。现已约定：③ 期间壳窗只允许被守卫自己导航，其他任何模块不得 close。

## 五、间接依赖登录态的功能（失败时怎么走）

| 功能 | 依赖方式 | 未登录时现状 | 是否有兜底 |
|---|---|---|---|
| 采集 `/api/collect_start` → `search()` | `_ensure_browse_page` 失败抛 `BrowserLoginRequiredError` | 抛错 → 前端引导登录 | ✅ 明确报错 |
| 搜索 `/api/search` | 同上 | 抛错 | ✅ |
| 笔记详情 `note()` / 作者 `user()` / 评论 `clients()` | 复用采集页点开 | 无活动页 → 返回 `{}` | ✅ 缺字段，不另开 URL |
| 克隆 `/api/clone` | 依赖详情字段 | 字段缺失则克隆内容不全 | ⚠️ 仅降级，未回归验证 |
| 客户聚合 `/api/clients_agg` | 依赖 `clients()` | fans 兜 0 | ⚠️ 同上 |
| 发布 `/api/publish` | 依赖登录态写入 | 未登录直接失败 | ⚠️ 未纳入登录前置检查 |
| Cookie 手工导入 `/api/import_cookie` | 与 `/api/auth/import_cookies` **两套并存** | 后者带状态验证，前者不带 | ⚠️ 两套口径，长期隐患 |
| Tab2 采集窗（`/login-hint`） | 页面内 fetch `/api/login_status` 决定显示「去登录」还是「开始采集」 | 依 ① 判定 | ✅ 但受 ① 假阳性影响（本轮已修） |
| keeper 窗口巡查 | 用 URL 识别壳窗/Tab2 | 壳窗被导航到 `/login` 时靠 coordinator 引用判活 | ✅ 已加保护 |
| 登录小窗截图流（mirror） | 拿"第一个小红书页"当目标 | 多页时可能截错页 | ⚠️ 优先级未定义 |

## 六、本轮修掉的三个 bug

| # | 现象 | 根因 | 修法 | 守护 |
|---|---|---|---|---|
| 1 | 打开登录窗 6 秒后登录页消失 | keeper `_keeper_sweep_blank` 把任何含 `/login` 的页当"残留登录页"关掉，与"登录窗初始页就是 /login"直接冲突 | 移除 `/login` 关闭分支，只清空白/新标签页（`_close_if_blank` + `_BLANK_URLS`） | `test_shell_window_unit.py` 49 例 |
| 2 | 点「去登录」→ 所有窗口关闭、应用退出 | `_refresh_engine_after_inject` 关闭"旧的小红书页"，而此刻那就是壳窗 → keeper 判"主窗被关"→ 自杀 | 改为不关闭任何页面，已有 `/login` 直接复用 | `test_browser_client_nav.py::TestImportInjectKeepShellGuard`（源码级断言无 `.close()`/`reload(`） |
| 3 | 登录守卫第一轮就退出，登录成功无法自动接管 Cookie | 守卫状态字典只有 `{"import": 0.0}`，`_guard_monitor_voluntary` 读 `state["inject"]` → `KeyError('inject')` | 补 `"inject": 0.0` | 守卫单测 + 实机日志复查 |

外加判定口径统一（第二节），这是"反复修反复出"的结构性成因。
