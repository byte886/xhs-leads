## 一、一句话

登录态不再被"查询"，而是被"事件告知"：采集每走一步就产出一条信号，撞到墙就暂停等人，人扫完码就自动接着采上次没采完的。

---

## 二、事件从哪来（零轮询）

| 事件 | 来源 | 触发时机 | 现有基础 |
|---|---|---|---|
| `progress` | `on_progress(n, items)` 回调 | 每采到一条卡片 | ✅ 已有 |
| `auth_wall` | `BrowserLoginRequiredError` 抛出 | 搜索/补全撞到登录墙或风控验证 | ✅ 已有（且页面保留供扫码） |
| `nav_login` | `page.on("framenavigated")` → URL 含 `/login` | 页面被动跳登录页 | 需新增（Playwright 原生事件） |
| `login_done` | 登录页 `framenavigated` 离开 `/login` + 握手三条判据 | 扫码成功 | 需新增（替代守卫现在 1 秒一次读 cookie） |
| `user_stop` | 前端点停止 | 手动 | ✅ 已有 |
| `page_closed` | `page.on("close")` | 采集窗被关 | 需新增 |

**结论：没有任何一条需要轮询。** 现在守卫"每 1 秒读一次 cookie"可以退役——扫码成功平台一定跳转，`framenavigated` 就是那个信号。

## 三、状态机

```
        ┌──────────────────────────────────────────┐
        │                                          │
     idle ──user_start──▶ running ──auth_wall──▶ paused_need_login
                            │  ▲                        │
                            │  └────login_done──────────┤
                            │                           │
                            ├──user_stop──▶ stopped_partial
                            │                           │
                            └──limit_reached──▶ done    └──timeout──▶ stopped_partial
```

| 状态 | 含义 | 左侧按钮 | 右侧窗口 |
|---|---|---|---|
| `idle` | 空闲 | 开始采集 | APP 或采集页 |
| `running` | 正常采集 | 停止 | 采集页滚动 |
| `paused_need_login` | **撞墙暂停，任务还在** | 「等待登录」置灰 + 「放弃」 | 登录页，等扫码 |
| `resuming` | 扫码成功，回补断点 | 「恢复中」 | 采集页 |
| `stopped_partial` | 用户放弃或超时 | 开始采集（可重来） | 不动 |
| `done` | 采满/平台不增长 | 开始采集 | 不动 |

**关键：`paused_need_login` 不结束任务。** 现在撞墙是 `status="error"` + 任务退出，数据不再增长；改后 worker 挂在 `await login_event.wait()`，不耗 CPU、不轮询、任务不消失。

## 四、一次撞墙的完整时序

```
① 采集 worker 在第 N 条上撞墙
   → browser_client 抛 BrowserLoginRequiredError(wall)，页面保留、不关闭
② worker 捕获它（不再当 error）：
   · 置 status = "paused_need_login"
   · 记断点：已入库的 note_id 集合（查表格，不用额外存）
   · 发 auth_wall 事件 → SSE 推左窗
③ 左窗收到：
   · 按钮变「等待登录」，列表刷新（已采的都在）
   · 提示：「已采集 N 条，因需要登录暂停。右侧窗口已打开登录页，请扫码。」
   · 把右侧窗口顶到前台
④ 右侧：应处于 /login（撞墙时页面本来就在登录墙，无需再导航）
   · 若不在 /login（是风控页/captcha）→ 才导航到 /login
⑤ 用户扫码
   · 平台自己跳 explore → framenavigated 事件
   · 握手三条判据全中 → 发 login_done 事件
⑥ worker 收到 login_done：
   · 置 status = "resuming"
   · 重新搜索同一关键词，跳过已入库的 note_id（见第五节）
   · 补满 limit 后 done；若再次撞墙 → 回到 ②
```

## 五、断点与续采（你说的"记住采到哪"）

**方案：不存游标，查表格。** 采到的每条都已逐条入库（`_rank_and_insert`），`note_id` 天然就是断点。

| 做法 | 说明 | 为什么 |
|---|---|---|
| 续采 = 重新搜索同条件 + 跳过已入库 id | 搜索本身是正常操作，不违反规则 | 小红书结果流会变（刷新后顺序/内容都不同），按页码续会漏会重 |
| 不写 cursor 字段 | 少一处状态、少一处不一致 | 表格是唯一事实源 |
| **必须绕过 `_reset_collection_data()`** | 现在每次 `collect_start` 都清空旧批次 | 不清空才能续；需加 `resume` 参数区分「新采集」和「续采」 |

⚠️ 现有代码里 `_reset_collection_data()` 无条件清空，是续采的第一个硬障碍，必须改。

## 六、暂停期间左窗做什么（你说的"评分排序 + 告知实际情况"）

现状：每条入库时已评分（`_rank_and_insert`），所以暂停时数据**已经带着分**。

所以暂停时做三件事：

| 动作 | 谁做 | 说明 |
|---|---|---|
| 刷新列表 | 前端 | 已采的 N 条全部可见，按现有分数排序 |
| 顶部状态条 | 前端 | 「已采集 N 条 · 因需要登录暂停 · 等待右侧扫码」 |
| 深评（可选） | 后端 | 如果有 LLM Key，利用等待窗口对已采数据补跑深度评分——**这是纯赚的时间**，但要标「可选」 |

## 七、异常分类与处置（不是所有异常都该去登录页）

你说的"异常了先驱动到登录页看能不能正常"，要分情况，否则会把网络抖动也当成登录问题，白白搭上一次风控额度。

| 异常类型 | 判别 | 处置 |
|---|---|---|
| 登录墙（页面要求登录/停在 /login） | `BrowserLoginRequiredError` | **直接暂停**，不重试，去登录页 |
| 风控验证（安全限制/captcha/「登录后查看」） | wall 文案命中 | 暂停 + 提示「需要人机验证」，页面保留 |
| 接口未登录（code=-100 / 401） | 响应体 code | 暂停，去 /login |
| 网络抖动/超时 | 请求异常、非业务码 | **先重试 2 次**（带间隔），仍失败才暂停 |
| 空结果（卡片 0 且无 wall 文案） | 产出为空 | 重试一次搜索；仍空 → 按「0 条完成」，**不判登录失效** |
| 被踢（登录超限/请重新登录） | 页面文案 | 暂停 + 清失效记忆，强制重新登录 |

## 十、产品细节与边界（实测补充，待对齐）

> 视角：真实使用者在电脑前会怎么点、会误会什么、哪里会卡住。

### 10.0 先定一条原则：用户在场且一眼能解决的事，不自动化

自动化的价值在于"用户不在场"或"用户做起来很麻烦"的事。用户点一下就好的事，自动化只会多出一处不确定性和竞态。

| 场景 | 谁做 | 理由 |
|---|---|---|
| 二维码过期，点「点击刷新」 | **用户** | 页面上就写着，一眼可见、一下就好 |
| 滑块/图形验证 | **用户** | 自动化尝试等于主动触发风控 |
| 清空已采数据 | **用户确认** | 破坏性操作不能替用户决定 |
| 扫码登哪个账号 | **用户选** | 只有用户知道自己要工作号还是私人号 |
| 续采跳过已入库、断点续采 | **系统** | 用户算不了，也不该算 |
| 登录态判定 | **系统** | 用户看不出来（页面看着正常其实已失效） |

### 10.1 二维码过期（记录，不作为问题）

登录页放置约两分钟后会显示「二维码已过期 / 点击刷新」，刷新入口是 `DIV.status-desc.refresh`，约 (451, 343)，57×16。

用户看得见、点得到，自己点一下就好。**本节不产生任何功能需求**，只留一条约束：登录页存活期间我们不做 `goto`、不 reload、不反复 evaluate，避免抢用户的操作。

### 10.2 按钮失效性（逐个状态定死，避免"看起来能点但点了出事"）

| 状态 | 主按钮 | 次按钮 | 绝不能出现 |
|---|---|---|---|
| `idle` | 开始采集 | — | — |
| `running` | 停止采集 | — | 「开始采集」（会触发清库重启） |
| `paused_need_login` | **灰化「等待登录」** | 「放弃剩余，用已采 N 条」 | 「开始采集」（会清空已采数据） |
| `resuming` | 灰化「恢复中」 | 「停止」 | 「继续」 |
| `stopped_partial` / `done` | 开始采集 | 「查看已采 N 条」 | — |

补充规则：

- `paused_need_login` 与 `running` 之间不允许出现"空窗"（任务状态一变化，按钮必须同帧切换），否则用户会在空窗里点到"开始采集"。
- 所有按钮点击做 300ms 去抖 + 服务端幂等（同一 task_id 的 resume 只接受一次），防连点双跑。

### 10.3 账号正确性（业务级风险，不只是体验）

扫码用的是**手机小红书 App 当前登录的账号**。如果用户手机上登的是私人号，工作号是另一个，扫完就登错了号。

后果不是"采不到"，而是"采到了错的数据 + 发布发错号"。

处置：登录成功后，右侧页面读出头像旁的昵称，左侧显示「已登录：<昵称>」，并允许「换号」再扫一次。这一步是产品必须给的确认位，不能默认用户扫对了。

### 10.4 登录成功之后的遮挡层——只提示，不代关

小红书登录后常见遮挡：青少年模式引导、隐私政策、版本更新提示、新人券。它们会让"点搜索框"失败，表现为**登录成功、按钮可点、采集 0 条**。

**口径：不自动关。** 弹窗是平台的业务流程，我们乱点可能点进别的页面、也可能因为判断错而关掉不该关的东西。按 10.0 的原则，用户看得见、关得掉，就交给用户。

我们做两件只读的事：

| 动作 | 内容 |
|---|---|
| 检测 | 页面存在已知遮挡特征（全屏遮罩 + 引导类文案）时，置一个"有遮挡"标记 |
| 提示 | 左侧状态条写「右侧页面有弹窗遮挡，请手动关闭后再继续」，并提供「重新检测」按钮 |

不点、不关、不猜。

### 10.5 暂停态其实是一个决策点，不是一个等待态

用户此刻真正要决定的是：**继续等登录，还是就用这些？**

只给"等待"会让用户干耗；建议三选一：

| 选项 | 适用 |
|---|---|
| 等登录，继续采 | 数据还差得远 |
| 就这些，去评分挑选 | 已有数据够用 |
| 放弃，重新换词 | 这批质量不行 |

并且暂停态要显示「已采 N 条 / 目标 M 条」——让用户判断值不值得等。

### 10.6 通知与"人不在"

扫码必须有人。用户可能离开电脑 10 分钟以上。需要：

- 系统通知（通知中心 + 可选声音）：「采集已暂停，请扫码继续」
- 回来后的提示不要用"已超时"这种否定说法，而应给「上次采到 N 条，是否继续」

### 10.7 采集进行中的手动干扰

采集时右侧窗口在滚动，用户手一滑：

| 用户动作 | 后果 | 处置 |
|---|---|---|
| 手动滚动列表 | 打断采集节奏、可能重复/漏采 | 采集期间提示"采集中，请勿操作"；不硬锁（锁了像死机） |
| 手动点笔记卡片 | 页面跳走，采集断 | 同上 |
| 关闭右侧窗口 | 采集立即中断 | 校验式确认：「关闭将中断采集（已采 N 条保留）」 |
| 导航到别处 | 登录页丢失 | 采集期间锁 URL 白名单，只允许平台自身跳转 |

### 10.8 "0 条"必须给归因

用户最容易失望的场景：登录着、按钮亮着、点了采集、什么都没有。

| 可能原因 | 提示 |
|---|---|
| 关键词太窄/筛选太严 | 「该条件下无结果，建议放宽筛选」 |
| 登录态实际失效 | 「需要重新登录」 |
| 页面有遮挡 | 「页面被弹窗遮挡，请手动关闭」 |
| 平台限制 | 「平台限制访问，建议稍后再试」 |

不给归因，用户只会认为工具坏了。

### 10.9 数据的破坏性操作要显式确认

`collect_start` 现在**无条件清空**旧采集数据。用户点了"开始采集"就丢上一批。

处置：库里已有 N 条时，按钮改为「重新采集（将清空 N 条）」，二次确认。

### 10.10 续采必须锁条件

暂停期间用户改了关键词/筛选，再点"继续"——续采按哪个条件？

处置：续采锁定中断时的条件快照；用户改条件视为**新任务**，需明确提示「条件已改，将作为新采集开始」。

### 10.11 多关键词排队

用户想一次采 5 个词，第 1 个撞墙暂停。剩下 4 个：排队等？还是直接放弃？

建议：队列保持，但**不自动跳过**——因为跳过等于"用户不知道哪个词没采"。状态条显示「1/5 暂停中，后面 4 个待采」。

### 10.12 风控的累积效应

同一个号一天内多次撞墙，说明账号已被标记。此时继续重试只会更糟。

处置：连续 3 次撞墙 → 提示「该账号今日访问受限，建议间隔数小时或更换账号」，不再自动重试。

### 10.13 部分数据的标记

中断的批次不是完整批次，导出/联系客户时要标注「部分采集（N/M）」，否则用户会当成全量结果用。


## 十一、轮询清零台账（R-6.53z8c · 用户拍板「轮形的都先去掉」）

判断标准两条，只有两条：

- **周期性重复读同一状态 = 轮询，必须去掉。**
- **等待页面渲染 / 拟人操作节奏 = 必要延迟，保留**（它不是状态查询，删了会破坏渲染与防风控）。

留存理由**不许写「不影响运行」**。用户明确否决过这条理由：留着会污染后续开发规划，后手容易遗忘并重复踩坑。

| 位置 | 原行为 | 现状 | 替代机制 |
|---|---|---|---|
| `CollectPanel.vue` 进度 | `setInterval` 1s 查 `collect_progress` | **已删** | 订阅 SSE `collect`；断线重连补拉一次 |
| `StatusBar.vue` | `setInterval` 2s 查 `status_now` | **已删** | 订阅 SSE `collect` |
| `App.vue` 登录守护 | `setInterval` 60s 查 `login_status` | **已删** | 订阅 `collect.paused_need_login` + `login` |
| `ForceLogin.vue` | `setInterval` 1s 查 `login_status` | **已删** | 打开对齐一次 + 订阅 `login` |
| `shell_window` 登录守卫 | `while` + `sleep(1)` 读 Cookie | **已删** | `page.on("framenavigated"/"close")` + 事件后 3 次短验证 |
| `browser_client` / `collect_pipeline` 的 sleep | 等渲染 / 拟人节奏 | **保留** | 非状态查询 |
| `shell_window` keeper 5s 兜底 | 5s 查壳窗存活 + Tab2 联动 | **已删** | 退出语义换到 close 事件（`_handle_close`→3s 校验→`_shell_closed_verify`）；右窗关闭改 `_schedule_tab2_rebuild` 一次性定时重建。keeper 主循环改为 `await asyncio.to_thread(stop.wait)`，零周期查询 |

### SSE 通道本身的两个例外（不算轮询）

- 服务端 30s 一次注释心跳（`: ping`）：只保活 HTTP 连接，不携带业务状态。
- 前端断线重连（`retry: 3000`）：浏览器自动重连，重连成功后各订阅者**补拉一次**当前状态做对齐，一次性同步，不是周期采样。

### 新增端点

`GET /api/events`：SSE，事件形状 `{kind, data}`。当前三类：`collect`（采集状态快照，见 `_state_snapshot`）、`login`（登录态变化）、`__open__`（前端本地合成，表示连接已建立/重连成功）。


## 十二、进程级看门狗（R-6.53z8e）

前面把业务轮询清零后，剩一个真问题：主进程被 `SIGKILL`、崩溃或卡死时，
`atexit`/信号处理器都不执行，引擎（CFT Chrome）会残留成孤儿——用户看到
「窗口关了但进程还在」。

这件事**不适合塞回事件循环**：主进程自己都快死了，它的定时器也救不了自己。
用户拍板：单独挂一个后台进程做总监控。

### 机制

- `backend/src/watchdog.py`，launcher 在 `asyncio.run` 之前 `watchdog.start()`。
- `os.pipe()` + `os.fork()`：父进程持写端，子进程持读端阻塞等待。
- 父进程**无论以何种方式消失**（正常退出 / SIGTERM / SIGKILL / 崩溃），
  内核都会关闭写端 → 子进程读端拿到 EOF → 立即 `pkill -9 -f <引擎特征>` → 退出。
- **零轮询**：没有 sleep 循环，没有定时器，靠内核事件唤醒。

### 与「业务轮询」的边界（用户口径）

- 业务状态同步（采集进度、登录态、窗口状态）一律走事件：SSE / `page.on` / `asyncio.Event`。
- 看门狗只回答「进程还在吗」，属 OS 层职责，不读任何业务状态、不碰窗口逻辑。

### 引擎特征串（避免误杀）

两条独立特征，命中任一即清理：

1. 内置 CFT 目录段（`.../engine/chrome-mac-x64`）；
2. 应用账号目录（`~/.xhs-leads/accounts`）。

都不会出现在用户日常 Chrome 的命令行里。

### 实机验证（2026-11-06）

```
清理前引擎进程：25787 25789 25791 25795 25796
kill -9 25780（主进程）
强杀后引擎进程：（空）
看门狗状态：已退出
```

注意：`pkill -9 -f launcher.py` 会连看门狗一起杀（fork 继承同一 argv），
手工清理时若要验证看门狗行为，用主进程 PID 精确 kill；日志里会打印
`[xhs-leads][watchdog] 看门狗已启动（pid=...）`。


### 日志（R-6.53z8f）

主进程被强杀时，它自己的日志往往来不及 flush，最后一行就是缺的。所以看门狗
自己写一份独立日志：`<data-dir>/watchdog.log`，与主日志的 fd 完全分离。

事件序列（正常一轮）：

```
[start]  主进程 pid / 看门狗 pid / 日志路径 / marker 列表
[armed]  等待父进程 EOF，监视 N 条特征
[eof]    父进程已消失（正常退出 / SIGKILL / 崩溃），开始清理引擎
[reap]   marker[i] 命中 N killed=N pids=... 失败=...
[exit]   清理完成，存活 Xs 后退出
```

- 每次清理**先 `ps` 拿 PID 列表再逐个 kill**，所以日志能写清「杀了谁」，
  而不是只留一句「已清理」。
- 空命中也必须留一行（`无命中`），否则「没杀到」和「压根没跑」区分不开。
- 单文件超过 512KB 滚成 `.1`，避免无限增长。
- 启动时读上一次最后一条事件：若不是 `exit`/`stop`，打一条
  `告警：上次运行疑似异常退出`——这是「上次到底怎么没的」的第一条线索。
- 主进程侧 `stop()` 也会落一条 `[stop]`，正常退出与异常退出因此可对照。

实机样本（2026-11-06 强杀验证）：

```
15:24:00 [start]  主进程 pid=26256 看门狗 pid=26258 markers=[chrome-mac-x64, accounts]
15:24:00 [armed]  等待父进程 EOF，监视 2 条特征
15:24:57 [eof]    父进程已消失，开始清理引擎
15:24:58 [reap]   marker[0] 命中 3 killed=3 pids=26263,26265,26267 失败=无
15:24:58 [reap]   marker[1] 无命中
15:24:58 [exit]   清理完成，存活 57.8s 后退出
残留引擎数：0
```

### 日志来源标签（R-6.53z8i）

原来只有 `%(name)s`（模块名），回答不了「是谁触发的」。现在加一列来源标签，
用标准库 `contextvars` 实现——不引第三方。

**标签分级**（冒号可多段，按排障需要定深度）：

| 标签 | 什么在打 | 埋点 |
|---|---|---|
| `win:shell` | 左壳窗自己的动作 | `keep_shell_tab` / `_keeper_init_pass` |
| `win:collect` | 采集窗（导航/显隐） | `_sync_collect_visibility` |
| `win:collect:rebuild` | 采集窗重建 | `_rebuild_collect_win_once` |
| `win:collect:login` | 采集窗上的登录流程 | `login_guard` |
| `worker:collect` | 一个采集任务从头到尾 | `_collect_worker` |
| `worker:collect:retry` | 撞墙→暂停等扫码→续采 | `_collect_run_rounds` |
| `worker:collect:round` | 单轮：搜索→逐条补全入库 | `_collect_round` |
| `bg:main` | 无窗口后台（默认） | 引擎、审计、启动期 |
| `bg:watchdog` | 看门狗 | `watchdog.log` 自成一格 |

**输出**：

```
2026-11-06 16:05:00 INFO [win:shell][src.shell] keeper 页面集=http://... shell_ref=None
2026-11-06 16:05:00 INFO [win:collect:login][src.shell] 启动已登录——守卫待命
2026-11-06 16:04:58 INFO [bg:main][src.engine] 引擎二进制: ...chrome-mac-x64/...
```

**为什么用 contextvars 而不是引第三方**：`structlog` 要改全部调用点、`loguru`
要换掉整套 backend、OpenTelemetry 对本地桌面应用太重。contextvars 是标准库，
只在入口包一层，整条调用链自动继承，asyncio 每个 task 复制 context、互不串味。

**已收编**：`shell_window.py` 46 处、`collect_pipeline.py` 10 处、`server.py` 1 处
的 `print` 全部改为 logging（原来是 `print("[xhs-leads][keeper] ...", flush=True)`，
既不进日志文件也没有级别）。级别按内容判定：含失败/异常/崩溃 → warning，其余 info。

**未收编**：`launcher.py` 的 15 处启动提示。它跨 sys.path 边界（logger 在
`_prepare_env` 里才可导入），强行统一会让代码变丑；而且这类「进程启动横幅」
与业务日志分开看反而清楚。`uvicorn` 的 HTTP access log 同理保持原格式。


**采集标签是三层嵌套，不是并列**：

```
_collect_worker        → [worker:collect]        一个任务：建连接→跑轮次→收尾落库
  └ _collect_run_rounds → [worker:collect:retry]  撞墙→暂停等扫码→续采
      └ _collect_round  → [worker:collect:round]  单轮：搜索→拿一批卡片→逐条入库
```

一个任务通常只跑一轮；撞到登录墙暂停、扫码恢复后再跑第二轮，此时 `retry`
会再调一次 `round`。三层分开的价值：日志里看到 `retry` 就知道「这任务被登录墙
打断过」，看到 `round 2` 就知道「恢复后又采了一批」，不用翻全量日志。


#### 标签边界核对（R-6.53z8j）

标签靠 `tagged` 装饰器在入口设一次、整条调用链继承。所以错标不是「名字写错」，
而是 **scope 边界把别的职责包进来了**。核对判据三条：

1. 标签名描述的动作 = 函数实际做的事（名实相符）
2. 函数内打的日志都真属于这个来源（不跨职责）
3. 粒度够不够：只凭标签能不能定位到问题

**核对结果**：8 个埋点按上述判据查，发现 5 处外溢——`keep_shell_tab` 打
`win:shell` 后，它调用的采集窗动作函数被一起染成 `win:shell`：

| 函数 | 原来标成 | 改为 | 它实际做什么 |
|---|---|---|---|
| `_match_collect_page` | `win:shell` | `win:collect:find` | 找采集窗页面 |
| `_calibrate_reused_collect_win` | `win:shell` | `win:collect:calibrate` | 复用采集窗的尺寸/位置校准 |
| `_keeper_setup_collect_win` | `win:shell` | `win:collect:setup` | 创建采集窗骨架 |
| `_close_if_blank` | `win:shell` | `win:collect:sweep` | 清空白/新标签页残留 |
| `_rebind_if_closed` | `win:shell` | `win:collect:login` | 登录守卫重绑定壳 tab 引用 |

修完 `[win:shell]` 下只剩真正的壳窗事（keeper 快照、Tab1 初始化、壳窗重建）。

**不需要全仓逐行查**：`bg:main` 这个默认值覆盖的代码（引擎、server、审计）不需要
再细分——`%(name)s` 第二列已经能区分 `src.engine` / `src.server` / `src.audit`。
真正要查的是「每个 tagged 入口的调用链里有没有跨职责日志」，这是有界的。
