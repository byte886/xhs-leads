# 按作者采客户 · 需求与原型

> 状态：**设计推演已定稿，未开发**（2026-11-08）
> 定位：独立功能、独立页面，与「采集」页的关键词搜索**完全解耦**
> 关联：`docs/project/待办事项.md`（K1）；原型 `docs/project/ui-review/k01-author-page.png`

---

## 一、这件事是怎么来的

1. 采集页卡片原先只有两个 hover 按钮：一键克隆、采集客户（单篇笔记的评论区）。
2. 用户提出还要能"按作者采"——把**同一个博主最近若干篇笔记的评论区**一起采，跨篇按人去重。
3. 之后连续追问两件更底层的事：
   - 「采完了，后续想看，又应该在哪里看呢？」
   - 「这个跟搜索关键字采集不一样，那个是临时的，但这个考虑到数据量的问题，可能需要做增量」。
4. 对齐过程中用户明确纠正过一次方向：**不是把作者采塞进客户 Tab 做二级切换**，而是

   > 「原先功能完全不动，用户可以从搜索到的卡片里面，去选择用户去单独采集，应该也可以单独搜索用户，再去采集。这是个独立的功能。也会有独立的页面」

所以本功能等于：一个跟「采集」平行的子系统（搜作者 → 采 → 看档案 → 增量更新），两边数据不混。

## 三、实测事实（决定设计能做到什么）

这些是用 CDP 真机取证得到的，不是推断，直接决定方案边界：

| 事实 | 证据 | 对设计的影响 |
|---|---|---|
| 作者主页卡片**只有标题和作者名** | 打开 `user/profile/676a7509…`，30 张卡 `innerText` 仅「标题 \| 作者名」 | 拿不到评论数，**无法预判哪篇涨了新评论** |
| 主页卡片也没有发布时间文本 | 同上 | "新发的笔记"只能靠 feed_id 与本地库比对得出 |
| 评论数只在**详情页**可见 | 采集时 `comment_count` 从详情页取，已入库 | "查老笔记"必须逐篇打开，约 5–6 秒/篇 |
| 主页一屏加载 30 张卡 | 同上 | 篇数上限 20 时也够用，无需深度滚动 |
| `notes` 表已存 `xsec_token`（46 位） | 表中实有；拼回 `explore/<id>?xsec_token=…` 可直开 | 逐篇采集不必依赖搜索页，直开即可 |
| 应用启动就清空 notes / clients | `server.py:81` `_reset_collection_data()`，启动时 `server.py:121` 调用 | **历史留不住**，"后续想看"当前不成立 |
| 每次点「开始采集」再清一次 | `CollectPanel.vue:203` → `/api/collect_clear` | 同上，且会连带清掉作者采的数据 |

## 四、现有系统的约束（动手前必须知道）

### 4.1 清空逻辑的来历（不是 bug，是旧前提）

`docs/project/采集与登录闭环操作流程SOP.md:58` 原文：

> **R-6.25**：新采集清空旧库（笔记+客户+采集图片），**保证库里只有本次数据**

当时只有关键词搜索一种采集入口，一次搜索=一批结果，"库里只有本次数据"是对的。

`docs/project/接口清单与合理性审计.md:85`（z8p 改动）原文：

> 清空是破坏性动作，藏在「开始采集」里会让**任何调 collect_start 的入口被动删数据**。现在前端按「先清 → 再开始」顺序显式调两次，用户看到的行为不变

即：**当时已经预见到第二种入口的风险，但只做了接口拆分，没做数据分区**。同一文件还写了 notes 层已改成"累加 + 按 feed_id 去重"，只有 clients 层仍被清。

结论：数据结构本来就能累积，是被主动清掉的。新增作者采必须显式分区，否则两种功能互相清数据。

### 4.2 其他约束

| 项 | 现状 |
|---|---|
| 顶栏 | `FlowBar.vue` 4-Tab：采集 → 创作 → 客户 → 设置；`.tab.cur` 白底 `#fff1e6` / 字 `#b05a1f` |

## 五、增量机制：快 / 全 两档

因为主页卡片看不到评论数，"提前告知哪篇有新评论"做不到，所以不做假预判，给用户两档自己选：

| 档 | 做什么 | 耗时（10 篇基准） | 会漏什么 |
|---|---|---|---|
| **快** | 拉主页列表 → 与本地库比对 feed_id → 只采**新出现的笔记** | 约 40 秒 | 老笔记后来新增的评论不采 |
| **全** | 逐篇打开采过的笔记读一次评论数 → 与上次快照比对 → **涨了的才滚到底采** | 约 2 分钟 | 基本不漏；打不开的篇会跳过并计数 |

要点：
- 「全」的省时来自**跳过滚动加载**：没变化的篇只读数字就关，约 6 秒；有变化的才滚 4–10 轮（每轮约 2.2 秒）。
- 两档都按 `uid + feed_id` 去重，重复的人不重复计入。
- 评论数快照存在笔记级，作为下次比对的基线。

## 六、界面结构（原型见 `ui-review/k01-author-page.png`）

顶栏由 4 个变 5 个：**① 采集 → ② 作者 → ③ 创作 → ④ 客户 → ⑤ 设置**。
「作者」插在采集之后，因为两者同属"取数"阶段。

| 区域 | 内容 |
|---|---|
| 左上 | 搜索框（昵称 / 主页链接 / 小红书号）+ 已采作者列表（篇数 · 客户数 · 上次采于） |
| 右上 | 作者头部：小红书号、主页现有几篇、上次采于；按钮「在平台打开主页」「更新采集」 |
| 右中 | 采集设置：篇数选择 + 快/全两档 + 与上次的差异提示 |
| 右中下 | 采集历史：每次一行（时间 · 类型 · 检查了几篇/几篇有变化 · 新增几人） |
| 右下 | 这位作者的客户：昵称 · 意向 · 代表评论 · "几篇下说过几次" |

设计稿里的数字（12 篇 / 91 条 / 31 人）均为**示例数据**，不是真实采集结果。

## 七、数据模型建议

不改既有表语义，只加分区标记与新表：

1. `notes` / `clients` 增加来源标记（如 `source`：`temp` / `author`）；`_reset_collection_data` 只删 `temp`。
2. 新增 `authors`：user_id、nickname、avatar、主页链接、last_collected_at、last_note_count。
3. 新增 `author_runs`：每次采集一行（时间、快/全、检查篇数、有变化篇数、新增人数），供"采集历史"直接读。
4. 笔记级保存 `comment_count` 快照（`notes` 已有该列，作为基线即可）。
5. 图片清理同步分区：作者档案的封面图不清；`user_` 前缀继续保留。

## 九、明确不做

| 不做 | 原因 |
|---|---|
| 后台定时轮询作者主页做"监控" | 明显风控信号，且主页无变更信号可读 |
| 关键词采集也做增量 | 平台没有增量接口，下次仍要完整搜一遍，只能跳过重复入库，省不到搜索本身，容易让人误以为"点一下就有新结果" |
| 主页卡片预判哪篇有新评论 | 实测卡片无评论数字段，做不到 |
| 在客户 Tab 里混排两种来源 | 用户要求原功能完全不动 |
