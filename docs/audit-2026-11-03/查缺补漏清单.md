## 四、总体结论与建议执行顺序

文档体系**需要一次集中查缺补漏，优先级整体偏高**。根因是两次未回写文档的形态跃迁：①B 方案（engine_pool 取代外部 Chrome CDP/钥匙串）落地后，`新机器部署手册`、`project-structure`、`ui-*checklist` 仍残留"外部 Chrome 9223 + `~/.codex-xhs-profile` + 手动允许调试"旧口径；②R-6.16 把"无头引擎+pywebview 壳+登录镜像"改为"有头 CFT 应用窗+壳窗内真实登录页"后，`需求变更-App内呈现形态.md`、`界面重构设计-对齐版.md` §九、PRD v1.4 D8 仍在传播旧形态。**新机器部署手册是最危险的操作性文档**（照它部署会复现已淘汰的手动 CDP 流程）。

测试资产方面：功能面回归（t/e1/b 系列）覆盖扎实、断言真实，是可用资产；但 R-6.22~6.29 连续七轮窗口治理产生的新行为几乎没有回归网——唯一的布局脚本 layout_verify 反而与最新关窗语义矛盾（按现状跑会误杀 dev 实例），未登录启动时序、窗口震荡、登录后 Tab2 联动三项零断言。

**建议执行顺序**：①先修 P0 测试缺口（G1 新脚本 + G2 修 layout_verify + G3 时变断言），约一个新脚本加改一节旧脚本即可兜底后续小迭代；②重写新机器部署手册并批量订正 P0 文档口径；③再排 P1（G4 登录闭环重写、e1_s6 退役标注、各清单/方案文档加推翻注）；④P2 随迭代顺手清理。`constitution/`、`quality-gates/`、`采集与登录闭环 SOP` 主体、`授权 ADR` 与代码吻合度高，仅需小步跟进 R-6.26~6.29 变更。
