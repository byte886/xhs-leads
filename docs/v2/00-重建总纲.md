## 二、新体系统一原则（不可协商）

1. **单一真相源**：需求只有 `docs/v2/01-范围基线.md`；测试只有 `docs/v2/02-测试架构.md`；决策只有 `docs/DECISIONS.md`。其余文档一律降级为参考，不得再出现"以本文为准"。
2. **AC 驱动**：每条验收标准必须有稳定编号 `AC-<域>-<序号>`，并落到三态之一——`automated`（有自动化测试 nodeid）/ `manual-gate`（人工闸口，登记原因与操作人）/ `out-of-scope`（明确不做，写理由）。没有第四态。
3. **旧物归档不删除**：`git tag pre-rebuild-2026-11-07` + 旧测试与脚本整体移入 `legacy/`，保留可回退，但不再进门禁、不再维护。
4. **机器可验证优先**：能用断言表达的约束，不写成"注意事项"。红线一律落成测试或 hook。
5. **人只做两件事**：拍板范围、审 AC。代码、用例、脚本、门禁全部可以机器跑。

## 三、四个阶段与验收出口

| 阶段 | 内容 | 出口判据 |

| **P1 需求基线** | 以代码为锚（44 路由 / 19 模块 / 10 组件）重建范围基线，逐条给 AC 编号与三态 | 01 文档中每个功能域无"待定"残留；`AC` 总数 ≥ P0 功能 × 1 |
| **P2 测试重建** | 按 T0-T4 五层重建用例；红线断言先行；AC-TRACE 机器生成 | 所有 `automated` 的 AC 有可跑 nodeid；红线测试 100% 绿；AC 覆盖率 100%（含三态登记） |

## 五、风险与止损

- **回归失守风险**：旧 321 条测试覆盖了大量异常分支（如 app_config 的 422 单态、import_cookies 过滤分支）。重建期主干不跑旧套件 = 裸奔。对策：P2 期间旧套件在 `legacy/` 每日跑一次做对照，直到新套件覆盖同等 AC 数再停。
- **重建半途而废**：P1 必须一次做完（范围基线不能分批），P2 可按域增量。若 P1 两周内无法收敛，退回到"只在旧体系上加红线测试"的最小方案。
- **产品范围决策未拍板**：01 文档中标注 `【待拍板】` 的条目不得超过 8 条，超出说明范围本身没想清楚，先开会。

## 六、与旧方案的关系

旧 `quality-gates/gates.yaml` 的**标准**保留两条（变异 0 存活、CRAP < 30），**工具链**不再作为门禁主体（替换为 T0-T4 分层 + AC 追溯 + 红线断言）。`constitution/`、`roles/` 作为补偿设计随 Claude Code 落地退出使用。
